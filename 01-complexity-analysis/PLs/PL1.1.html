CARRERA: Computación ASIGNATURA: Estructura de Datos
NRO. PRÁCTICA: PL1.1 TÍTULO PRÁCTICA: Comparativa de métodos de ordenamiento y benchmarking
OBJETIVO
  • Construir un generador de números enteros aleatorios y una clase de benchmarking capaz de medir operaciones recibidas mediante una interfaz funcional.
  • Comparar un método básico de ordenamiento, un método investigado y dos variantes de ordenamiento de la biblioteca estándar de Java.
  • Almacenar objetos con el nombre del método, sample y duración en una lista de resultados e imprimirla completa al finalizar las mediciones.
  • Analizar resultados reales, relacionando tiempo observado, tamaño de entrada, representación de datos y complejidad algorítmica.
  • Investigar y explicar la implementación concreta de Merge Sort o Quick Sort incorporada al proyecto.
CONTEXTO

Se requiere una aplicación de consola en Java que genere muestras numéricas y compare distintas formas de ordenarlas. Todas las variantes deben producir el mismo orden ascendente y conservar los valores con sus repeticiones. La medición se realizará mediante una clase propia que reciba la operación a ejecutar, sin depender de un algoritmo específico.

En clase se desarrollará un ejemplo del flujo completo: generar datos, preparar una copia, enviar el ordenamiento mediante una lambda, medir la duración, comprobar el resultado y registrar la medición. La práctica amplía ese flujo con un algoritmo investigado, variantes de biblioteca y un informe reproducible.

La actividad tiene dos entregables evaluados de forma independiente: el proyecto comparativo con su README y la investigación del algoritmo con su implementación identificada en el mismo repositorio. Cada entregable se califica sobre 10 puntos.
RECURSOS
  • JDK y editor o IDE. Registrar la versión de Java, sistema operativo, procesador y memoria del equipo utilizado para las mediciones.
  • Git y repositorio remoto accesible para el docente. Trabajo individual; fechas de entrega establecidas en el AVAC.
  • Biblioteca estándar de Java, interfaces funcionales, expresiones lambda, arreglos y archivos Markdown. No se requieren dependencias externas.
  • Material de clase y fuentes técnicas identificables para estudiar Merge Sort o Quick Sort.
INSTRUCCIONES

1. Generación de muestras

  1. Implementar un método que reciba n y genere exactamente n números enteros aleatorios entre 0 y n, ambos inclusive. Se permiten valores repetidos; no se exige que aparezcan todos los valores del intervalo.
  2. Para n = 0 devolver un arreglo vacío. Para n negativo rechazar la solicitud con un error explícito. Documentar el rango de tamaños soportado y evitar el desbordamiento al calcular el límite superior del generador.
  3. Generar una sola muestra base por tamaño. Todas las variantes deben recibir copias independientes con exactamente los mismos valores y el mismo orden inicial.

2. Variantes obligatorias

ID Variante Datos y criterio Condición
V1 Método básico Arreglo int[]; orden ascendente. Escoger e implementar uno: Burbuja, Selección o Inserción. Identificar la variante utilizada.
V2 Método investigado Arreglo int[]; orden ascendente. Escoger e implementar uno: Merge Sort o Quick Sort. Explicar esa implementación en INVESTIGACION.md.
V3 Arrays.sort Arreglo int[]; orden ascendente. Usar el método de la biblioteca como referencia de rendimiento.
V4 Arrays.sort con Comparator Arreglo Integer[]; orden ascendente numérico. Definir un Comparator<Integer> mediante una lambda o un constructor de comparadores. Usar una comparación segura, sin restar valores.

Comparator define el criterio de comparación; no constituye un algoritmo de ordenamiento adicional. V4 utiliza objetos Integer y una sobrecarga diferente de Arrays.sort. Sus resultados corresponden a esa combinación de representación y mecanismo; no permiten atribuir toda diferencia de tiempo al comparador.

V1 y V2 deben realizar el ordenamiento mediante su propia lógica, sin delegarlo a Arrays.sort, Collections.sort, List.sort ni streams ordenados. La biblioteca sí se permite en V3, V4 y la verificación, fuera de la medición de V1 y V2.

3. Clase de benchmarking reutilizable

  1. Recibir la operación ejecutable, su nombre y el tamaño real de la muestra. Devolver un objeto con los resultados requeridos.
  2. Utilizar una interfaz funcional para enviar la operación mediante una lambda. Se admite Runnable para operaciones sin retorno o Callable<Void> si se conserva el diseño trabajado en clase; documentar el contrato elegido.
  3. Medir con System.nanoTime() inmediatamente antes y después de ejecutar la operación. Conservar la diferencia en nanosegundos como long y obtener milisegundos mediante división entre 1 000 000.0.
  4. Devolver un objeto de resultados, por ejemplo Resultado o Results, con nombre del método, sample y duración en nanosegundos. El tiempo en milisegundos puede calcularse al consultar o presentar el resultado. sample representa la cantidad de elementos ordenados.
  5. Mantener la clase independiente de los ordenamientos: no debe contener un switch ni condiciones por nombre para seleccionar algoritmos. La selección y preparación se realizan en el controlador de experimentos.
  6. Si la operación falla, conservar el motivo y la excepción original. Registrar el fallo fuera del intervalo medido; no convertirlo en una ejecución exitosa con duración cero. Corregir la causa antes de completar los 12 resultados válidos de la entrega.

4. Preparación y límites de la medición

El intervalo medido incluye la llamada que ordena la muestra y el trabajo interno necesario para completarla. Si la implementación de Merge Sort reserva su arreglo auxiliar dentro del método, esa reserva forma parte de su tiempo. Identificar esa decisión en el informe.

  • Antes de iniciar el cronómetro: generar la muestra original, preparar la representación Integer[] para V4, crear un clon nuevo de la entrada de cada variante, construir el comparador y crear la operación que se enviará al medidor.
  • Después de detenerlo: construir el objeto de resultados, validar el orden y la conservación de elementos y agregar el resultado válido a la lista administrada por el controlador. Imprimir la lista completa únicamente al finalizar todas las mediciones.
  • No copiar ni generar los datos dentro de la lambda medida. No imprimir el arreglo, guardar archivos ni ejecutar validaciones dentro de la operación cronometrada.
  • Cada ordenamiento debe recibir un clon nuevo de su arreglo base original. No reutilizar el arreglo ya ordenado por una ejecución anterior.
  • Las copias de entrada y la conversión de representación quedan excluidas del tiempo informado. Esta decisión debe declararse; el resultado no representa el costo total de preparar y procesar una solicitud.

5. Tamaños de muestra y almacenamiento de resultados

Utilizar los tamaños obligatorios 10 000, 50 000 y 100 000 elementos. Para cada tamaño, generar una única muestra de números aleatorios entre cero y dicho tamaño, ambos inclusive.

  1. Conservar el arreglo original sin modificar. Las cuatro variantes deben trabajar con los mismos valores y el mismo orden inicial.
  2. Antes de cada ordenamiento, crear un clon nuevo del arreglo original. No reutilizar un arreglo que ya haya sido ordenado por otra ejecución.
  3. Para la variante con Comparator, preparar un arreglo Integer[] con los mismos valores y en el mismo orden que la muestra original. Crear una copia independiente antes de ordenarlo.
  4. Realizar la generación, conversión y clonación fuera del intervalo de medición. La operación enviada al benchmarking debe ejecutar únicamente el ordenamiento.
  5. Ejecutar cada variante una vez por tamaño. La clase de benchmarking debe devolver un objeto Resultado o Results con el nombre del método, el sample y la duración obtenida.
  6. Agregar cada objeto devuelto a una lista de resultados, administrada por la clase que coordina las pruebas. La lista debe conservar las mediciones de todos los métodos y tamaños.
  7. Verificar después de cada medición que la salida esté ordenada y conserve todos los elementos. Esta comprobación debe realizarse fuera del cronómetro.
  8. Al finalizar todas las pruebas, recorrer e imprimir la lista completa de resultados. Cada registro debe mostrar el método, el tamaño de muestra y el tiempo en milisegundos.

La ejecución completa debe producir 12 resultados: cuatro variantes por tres tamaños. El campo sample representa la cantidad de elementos ordenados.

Si una ejecución falla, identificar y corregir su causa. No registrar cero como sustituto de una medición fallida ni presentar tiempos inventados.

Los tiempos corresponden a ejecuciones concretas en el equipo utilizado. Una sola medición por método y tamaño no permite afirmar que un método será siempre más rápido.
